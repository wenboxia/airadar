# 设计决策日志（面试题答案库）

> 每条格式：背景 → 选项 → 决定 → 为什么。新决策往后追加，不删旧条目（错了就加"修订"）。

## D1：手写 agent loop，不用 LangGraph / AutoGen

- **背景**：pipeline 需要编排 6 个步骤 + 条件路由（置信度三分支）。
- **选项**：LangGraph（图编排）/ AutoGen（多 agent 对话）/ 手写。
- **决定**：手写（pipeline/main.py，~30 行编排逻辑）。
- **为什么**：我们的拓扑是"线性链 + 一个条件路由"，LangGraph 的价值（循环图、检查点、多 agent 状态机）在这里用不上——引入它是拿框架复杂度换简历名词。框架的能力边界判断：任务拓扑是 DAG 且节点 < 10 时，框架的调试成本高于收益；真正需要 LangGraph 的场景是有环（agent 自我修正循环）、需断点续跑、多 agent 抢占共享状态。**面试价值：能说清"为什么不用"证明了解它的能力边界，比"用了"更有说服力。**

## D2：LLM 不联网，抓取由代码完成

- **背景**：需要"联网获取信息"，直觉方案是选带 websearch 的 LLM。
- **选项**：LLM 自带联网搜索 / 代码抓取信源 + LLM 只处理文本。
- **决定**：后者。
- **为什么**：①可控——信源 100% 由白名单决定，LLM 搜索会引入不可控来源；②可测——幻觉率的计算前提是手里有原文，摘要对照原文才能核验；③可溯源——每条内容标注 [来源] 和原文链接。生产级资讯系统的标准架构就是"工具层抓取 + 模型层处理"。LLM 联网只留给 Phase 2 的对话问答场景。

## D3：零服务器架构（GitHub Actions cron + 数据存 repo + Vercel 静态前端）

- **背景**：要"真实上线每天自动跑"，但不想维护服务器。
- **选项**：云服务器 + 数据库 / Serverless 函数 + 托管 DB / GitHub Actions + repo 即数据库。
- **决定**：GitHub Actions 每日 cron 跑 pipeline → SQLite/JSON commit 回 repo → Vercel 自动重新部署静态前端。
- **为什么**：零成本、零运维、天然有数据版本历史（每天一个 commit 就是审计日志）、失败自带邮件告警。代价：无实时后端（对话问答做不了——所以它去了 Phase 2）、数据规模有上限（个人知识库量级完全够）。**取舍思路：架构服务于产品阶段，不为想象中的规模设计。**

## D4：LLM 选型 = 方法论而不是站队

- **背景**：主力模型选 DeepSeek / Kimi / GLM / Claude？
- **决定**：①客户端 provider 无关（全走 OpenAI 兼容协议，换模型=改配置）；②默认 deepseek-chat（便宜+中文强）；③选型结论用自建黄金集实测得出（Week 3 多模型对比实验），不靠猜；④LLM-as-Judge 裁判**故意用与主力不同家的模型**——避免 self-preference bias（模型评自己输出会系统性偏高）。

## D5：命名 AIRadar

- **过程**：TradeWinds（被主人否：名字必须含 AI、与 AI 资讯相关）→ AIRadar（主人拍板）。
- **为什么成立**：雷达意象三合一——每天定时扫描（cron pipeline）、过滤杂波（信源筛选）、航迹跟踪（话题时间线=记忆）。名字不塞属性，属性交给 slogan：「每天扫描 AI 前沿、沉淀为知识库的情报 Agent」。产品命名原则：名字管记住，slogan 管说清（参照 Cursor/Copilot 都不解释自己）。

## D6：HITL = 置信度路由 + GitHub Issue 审批卡片

- **背景**：全自动会放走坏内容，全人工回到技术周刊的人力瓶颈。
- **决定**：triage 综合分（tier 基础分 55% + LLM 价值分 45%）三分支：高分自动发布 / 中间区开 GitHub Issue 勾选审批 / 低分丢弃留日志。Tier D 信源强制送审（新信源无信誉记录，不给自动发布权）。审批决策写 feedback.jsonl，每周回流：信源近期通过率持续走低 → 自动产生降 tier 建议（数据飞轮）。
- **为什么用 GitHub Issue**：零基建的异步审批收件箱，天然有通知、有审计记录，Actions 有权限读写。对标的是企业级 Agent 平台里"高风险操作强制人工审批卡片"的同构简化版。

## D7：降级路径的设计原则——保守降级

- **决定**：LLM 不可用/超预算时：S/A 信源放行、B/C/D 全部送人工审；摘要环节降级为"仅标题+链接入库"并打标。
- **为什么**：降级的方向必须是"宁可多麻烦人，不可错发内容"——发布质量是产品信任的底线，降级时收紧而不是放宽自动化权限。所有降级留痕（item.notes + stats），可审计可复盘。预算硬上限（token/调用次数）保证跑不穿钱包。

## D8：Anthropic 信源接入（真实的信源工程案例）

- **背景**：Anthropic 官网无 RSS（2026-08 核实 anthropic.com/rss.xml 404）。
- **过程**：RSSHub 公共实例（rsshub.app）→ 实测 403（公共实例限流不可靠）→ 社区镜像 Olshansk/rss-feeds（GitHub Actions 自动生成的 RSS，raw.githubusercontent 直读）→ 实测 200 且当天内容在列 → 采用。
- **启示**：权威信源 ≠ 好抓的信源；信源工程需要"官方 → 社区镜像 → 兜底记录失败"的层级方案。单信源失败不阻塞全局（fetch 层 try/except per source）。

## D10：跨厂商降级链（primary → fallback → 优雅退场）

- **背景**：主人同时提供了 DeepSeek / Kimi / GLM 三家 key。三家都用，但角色必须分清，不能"随便挑一个"。
- **决定**：三家各司其职——
  - **主力（干活）**：DeepSeek `deepseek-v4-pro`——中文强、便宜，pipeline 的 triage/摘要/分类都用它
  - **备用（兜底）**：GLM `glm-5.3`——主力出现**永久性故障**时自动接管（跨厂商，避免单一供应商故障导致整条 pipeline 瘫痪）
  - **裁判（评测）**：Kimi `kimi-k3`——只在评测环节当 LLM-as-Judge，**故意与主力不同家**，避免模型给自己的输出打高分（self-preference bias）
- **实现要点**：供应商永久性故障后**标记作废，本次运行不再尝试**——不是每条内容都重试一遍。这是效率的关键：50 条内容 × 3 个 stage 的场景下，这个设计省掉约 25 分钟的无效等待。
- **模型清单来源**：直接查各家 `/models` 接口实测（2026-08-28），不靠记忆猜测——LLM 的训练知识对模型版本这类高频变动信息天然过期。实测发现 DeepSeek 已是 v4 代、Kimi 已到 k3、GLM 已到 5.3，全部新于我的知识截止。**教训：涉及模型/API 版本，先查再写。**

## D11：429 不等于限流——错误分类必须看语义，不能只看状态码

- **背景**：配好三家 key 后首次冒烟测试，三家全部调用失败。
- **发现**：同样是"账户没钱"，三家返回的状态码完全不同——DeepSeek 返回 **402**（标准的"需要付款"），而 **Kimi 和 GLM 都返回 429**（通常表示限流）。
- **问题**：我原来的重试逻辑把 429 一律当作"可重试的限流"，会对余额不足这种**永久性故障**做三次指数退避重试（1.5s+3s+6s）。50 条内容的日常运行会空转约 25 分钟才失败退出。
- **决定**：错误分类不看状态码，看**语义**——429 的响应体里若命中余额/配额特征词（insufficient balance / suspended / 余额不足 / 无可用资源包 / quota），判定为永久性故障，立即换供应商，绝不重试。
- **验证**：写了 12 个回归测试锁住这套逻辑（`evals/test_llm_guards.py`），并在真实的三家零余额环境下做了端到端降级演练——主力 402 → 备用 429（语义识别为永久）→ 全挂 → 三个 stage 各自降级 → pipeline 照常跑完并发布了 3 条 S 级内容。
- **面试价值**：这是"兜底逻辑"从口号变成真东西的分水岭。绝大多数人写重试只按状态码，而真实世界的 API 语义是混乱的——**只有真跑过、真失败过，才会知道这件事**。

## D12：模型适配层——"OpenAI 兼容"并不真的兼容

- **背景**：三家都号称 OpenAI 兼容协议，但首次真实调用时两家直接报错或返回空。
- **实测差异**（2026-08-28）：
  - `kimi-k3` 只接受 `temperature=1`，传 0.2 直接 HTTP 400。
  - **三家的旗舰模型全都是推理模型**（deepseek-v4-pro / kimi-k3 / glm-5.x 都返回 `reasoning_content`），而**内部思考的 token 也计入 `max_tokens`**。实测 glm-5.3 在 `max_tokens=300` 时，思考就用掉 299 个 token，`content` 返回空字符串、`finish_reason=length`。deepseek-v4-pro 连"输出 {"a":1}"这种琐碎请求都要花 108 个思考 token——这正是首次运行时摘要环节 JSON 解析失败的真正原因。
- **决定**：加一层**模型适配层**（`llm.py` 的 `MODEL_QUIRKS`），按模型名前缀声明每家的怪癖（温度约束、token 倍率），调用逻辑不变。另加**自愈机制**：检测到"空 content + finish_reason=length"就自动加倍预算重试一次。
- **为什么这样分层**：新增模型只改一张表，不动调用代码；怪癖是**数据**不是**逻辑**。这对应 Agent 平台里"Tool 协议适配层"的思路——上层要一个统一契约，下层的脏活集中在适配层消化。
- **面试价值**：这是"模型能力边界"的具体体感。推理模型的 `max_tokens` 语义变了（要覆盖思考+输出），不知道这件事的人会在生产环境遇到"模型莫名返回空"，且极难排查。

## D13：内容获取降级链（直接抓取 → Jina Reader → RSS 简介）

- **背景**：首次真实运行发现 **OpenAI 的全部条目**都抓不到正文（`fulltext_failed`），RSS 里只有 150 字的一句话简介。
- **排查**：openai.com 由 Cloudflare 防护，实测直接抓取 403，**换成完整浏览器 UA 依然 403**——它拦的是非浏览器客户端本身。
- **决定**：内容获取也做降级链（与 LLM 降级链同构）：直接抓取 → Jina Reader（`r.jina.ai`，第三方正文提取服务，实测能拿到 53,975 字）→ 失败则保留 RSS 简介。每层结果记入 `item.extra.content_source`，前端可展示"内容完整度"。
- **取舍**：引入了一个外部依赖（Jina），但它只是兜底层、失败不阻塞，且换来了权威信源的完整正文——这是值得的交换。

## D14：信息不足时不许模型硬编（真实幻觉的根因修复）

- **背景**：首次真实运行的幻觉自检**抓到了一条真幻觉**——摘要写"loveholidays 用 Codex 让**全公司员工都能构建软件**"，而原文只说"让软件开发在整个企业内变得**可及**"。
- **归因**：这不是模型不老实，是**我们的 prompt 逼它编**——只给它 150 字的简介，却要求写 250-350 字的摘要，缺的信息只能靠猜补足。
- **决定**：`summarize` 按原文长度分两种模式。原文 < 400 字进入**简介模式**：只写一句话概括、`summary_long` 故意留空，prompt 明确告知"你拿到的只是简介，绝对不许推测或扩写"。前端据此展示"内容完整度"标记。
- **面试价值**：这是幻觉治理的正确姿势——**先归因再修**。归因结论是"评测问题/数据问题/prompt 问题/模型问题"中的**prompt 与数据问题**，而不是换个更强的模型。同一逻辑还有旁证：Kimi k3 只看标题时曾编造"这是 Anthropic 的愚人节玩笑"（重跑一次又变正常，说明是随机幻觉），喂上原文后判断完全准确——**信息不足是幻觉的第一诱因**，这反过来验证了 D2（自己抓原文再喂给模型）。

## D15：并发化——从 8 分钟 6 条到全量可用

- **背景**：首次真实运行 6 条内容耗时 **8 分 05 秒**（每条 80 秒）。推理模型单次调用要 5-30 秒，而每条内容要经过 triage/summarize/幻觉自检/classify 共 3-4 次调用。按此速度，40 条内容的日常运行要接近 1 小时。
- **决定**：抓取与三个 LLM stage 全部改为线程池并发（`guards.parallel_map`，标准库 `ThreadPoolExecutor`，不加新依赖）。并发度默认 6。
- **必须配套的正确性处理**：共享状态加锁——`Budget`（`+=` 在多线程下不是原子操作，会漏记 token 导致预算失控）、`LLMClient.stats`、供应商作废标记（避免重复打印降级日志）。单条失败仍被隔离，不影响同批其他条目（舱壁原则的并发版）。
- **为什么用线程而不是 async**：LLM 调用是纯 I/O 等待，线程池足够；改 async 要把 requests 换成 httpx 并重写整条链路，收益不抵成本。

## D16：并发度是被限流打出来的，不是拍脑袋定的

- **背景**：并发度设 6 跑全量后，日志里出现 GLM 的 `429 code 1302 您的账户已达到速率限制`，导致部分条目"所有供应商均不可用"而降级。
- **决定**：并发度降到 4；同时把临时性故障的退避从"3 次 / 基数 1.5 秒"改成"4 次 / 基数 4 秒"——真限流需要几十秒才恢复，退避太快只会继续把配额打满，形成自我强化的失败。
- **配套**：真限流（TransientError）与余额不足（permanent）走完全不同的路径，这正是 D11 那次错误分类修复的价值兑现——如果两者混在一起，这里要么该退不退，要么不该退瞎退。
- **面试价值**："并发度设多少"没有理论最优解，只能压出来。有意义的是**有没有观测手段发现它、有没有机制在它发生时不崩**。

## D17：让系统自愈，而不是手工调参

- **背景**：全量运行后发现 triage 有 2 条 `llm_json_invalid`、classify 有 9 条降级到启发式规则。根因还是 D12 那个推理模型问题——triage 给了 200 token、classify 给了 150 token，思考一花完就没预算写 JSON 了。
- **两种修法**：(a) 手工把每个 stage 的 max_tokens 调大；(b) 让客户端检测到截断（`finish_reason=length`）就自动加倍预算重试。
- **决定**：**两个都做，但以 (b) 为主**。原先的自愈只处理"content 完全为空"，现在扩展为"只要被截断就自愈"——因为截断的另一种形态是"半截 JSON"，解析失败但 content 非空，原逻辑漏掉了它。
- **为什么**：手工调参是一次性的，换个模型、改个 prompt 长度就又失配；自愈是结构性的。**能让系统自己恢复的，就不要靠人记得调参数。**

## D18：幻觉的第二个根因——元数据被当成了正文

- **背景**：修复 D14 后跑全量，幻觉检测抓到 4 条。逐条归因发现其中 3 条同源。
- **真实案例**：
  - 摘要写"**谷歌 DeepMind** 宣布…"，但原文通篇只说 Google——模型把**信源名**（Google DeepMind Blog）当成了文章内容。
  - 摘要写"**Simon Willison** 引用了 Paul Dix 的观点"，原文根本没提 Simon——博客主的名字被写成了文章作者。
  - 一条 HN 条目，模型从标题"CEO fired developers to make room for AI"编出整段背景故事，而该链接的实际内容是一个开源项目介绍（**HN 的标题是网友写的，与链接文章不是一回事**）。
- **归因**：不是模型能力问题，是 **prompt 设计问题**——我们把标题、来源名和正文平铺在一个 prompt 里，模型无从区分哪些是"关于这篇文章的元数据"、哪些是"这篇文章说了什么"。
- **决定**：① prompt 里用分隔线把【元数据（仅供参考，不是文章内容）】和【原文】明确切开；② 加三条铁律：元数据不是内容、不许补背景、不许外推结论。
- **验证（受控实验）**：拿被标记的原条目用新旧 prompt 各跑一遍——"谷歌 DeepMind"→"Google"修复；HN 那条改为正确摘要真实文章内容；"Simon Willison"张冠李戴消失。
- **意外收获**：修复后裁判在同一条上抓到了**更隐蔽的一类幻觉**——摘要漏掉原文的前提条件（"在构建验证系统并给予适当方向的前提下"），把有条件的结论表述成了无条件。这类"因省略而失真"比"无中生有"难发现得多，说明 LLM-as-Judge 确实在产生规则校验给不了的信号。
- **面试价值**：完整演示了 JD 里点名的归因能力——**从失败轨迹抽象假设 → 设计受控实验 → 验证 → 判断是模型问题还是 Harness 设计问题**。这里两次归因结论都是 Harness/prompt 问题，而不是"换个更强的模型"。

## D19：已知运行约束——个人账户的速率限制

- **现象**：36 条内容的一次运行要打 ~122 次 LLM 调用（每条约 3.4 次：评分/摘要/幻觉自检/分类），期间数次撞到 GLM 的 `429 code 1302 速率限制`，个别条目最终降级。
- **现状**：并发度 4 + 4 次退避（基数 4 秒）下，降级率已从 17% 降到 3%（36 条里 1 条）。
- **尚未做但已知的优化方向**（Week 3 视情况）：按供应商维度做令牌桶限速、把幻觉自检改为抽样而非全量、给 triage 用更便宜的 flash 模型（`deepseek-v4-flash` 实测 2.4 秒 vs pro 的 5.6 秒且评分质量相当）。
- **诚实记录**：这是个人账户的额度限制，不是架构缺陷；但**知道自己的瓶颈在哪、有没有可选的降本方案**，本身就是 Token 治理能力的一部分。

## D20：前端设计——雷达不是装饰，是数据可视化

- **背景**：前端要在 3 秒内让人（尤其是面试官）看懂这个产品在干什么。
- **决定**：整体走「仪表盘 / 信号情报终端」——深色仪器底、琥珀色代表有效信号、青色代表结构与扫描。字体用 Instrument Serif 做刊头 + IBM Plex Mono 做数据读数 + IBM Plex Sans SC 做中文正文，制造「编辑部 × 仪器」的张力（这正是产品定位：干的是资深编辑的活，用的是机器的方式）。
- **签名元素**：右栏的雷达示波器**绑定真实数据**——半径 = 综合分（越靠中心越可信）、角度 = 内容分类扇区、颜色 = 时间维度（琥珀=时效 / 青绿=长期价值）、大小 = 分数。筛选时雷达同步更新：点「论文」，5 个绿点；切到「待审队列」，光点全部落在外圈。**隐喻和数据是一致的，不是套壳。**
- **「机制」页**：产品的自我说明书——pipeline 六环节、信源分层准入逻辑、置信度路由阈值、三条降级链（附真实故障案例）、评测方法、最近一次运行的真实读数。面试官打开这一页就能看懂整个系统。
- **诚实标注**：抓不到原文的条目在卡片上标「简介级」并说明原因。**承认信息不完整，比假装完整更可信**——这与 D14 的反幻觉原则一脉相承。
- **可读性实测**：深色底上 300 字重的中文过细，实测调到 400 才清晰；正文对比度也相应上调。

## D9：discarded 条目也入库

- **决定**：被筛掉的内容不是删掉，而是以 discarded 状态入库。
- **为什么**：①审计——"筛掉了什么"和"收了什么"同样是筛选器质量的证据；②评测——黄金集里 include=false 的样本需要 pipeline 决策记录才能算 precision/recall；③回溯——阈值调整后可以复盘历史误杀。

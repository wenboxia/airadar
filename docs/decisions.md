# 设计决策日志（面试题答案库）

> 每条格式：背景 → 选项 → 决定 → 为什么。新决策往后追加，不删旧条目（错了就加"修订"）。

## D1：手写 agent loop，不用 LangGraph / AutoGen

- **背景**：pipeline 需要编排 6 个步骤 + 条件路由（置信度三分支）。
- **选项**：LangGraph（图编排）/ AutoGen（多 agent 对话）/ 手写。
- **决定**：手写（pipeline/main.py，~30 行编排逻辑）。
- **为什么**：我们的拓扑是"线性链 + 一个条件路由"，LangGraph 的价值（循环图、检查点、多 agent 状态机）在这里用不上——引入它是拿框架复杂度换简历名词。框架的能力边界判断：任务拓扑是 DAG 且节点 < 10 时，框架的调试成本高于收益；真正需要 LangGraph 的场景是有环（agent 自我修正循环）、需断点续跑、多 agent 抢占共享状态。**面试价值：能说清"为什么不用"证明了解它的能力边界，比"用了"更有说服力。**

## D2：LLM 不联网，抓取由代码完成

- **背景**：需要"联网获取信息"，直觉方案是选带 websearch 的 LLM。
- **选项**：LLM 自带联网搜索 / 代码抓取信源 + LLM 只处理文本。
- **决定**：后者。
- **为什么**：①可控——信源 100% 由白名单决定，LLM 搜索会引入不可控来源；②可测——幻觉率的计算前提是手里有原文，摘要对照原文才能核验；③可溯源——每条内容标注 [来源] 和原文链接。生产级资讯系统的标准架构就是"工具层抓取 + 模型层处理"。LLM 联网只留给 Phase 2 的对话问答场景。

## D3：零服务器架构（GitHub Actions cron + 数据存 repo + Vercel 静态前端）

- **背景**：要"真实上线每天自动跑"，但不想维护服务器。
- **选项**：云服务器 + 数据库 / Serverless 函数 + 托管 DB / GitHub Actions + repo 即数据库。
- **决定**：GitHub Actions 每日 cron 跑 pipeline → SQLite/JSON commit 回 repo → Vercel 自动重新部署静态前端。
- **为什么**：零成本、零运维、天然有数据版本历史（每天一个 commit 就是审计日志）、失败自带邮件告警。代价：无实时后端（对话问答做不了——所以它去了 Phase 2）、数据规模有上限（个人知识库量级完全够）。**取舍思路：架构服务于产品阶段，不为想象中的规模设计。**

## D4：LLM 选型 = 方法论而不是站队

- **背景**：主力模型选 DeepSeek / Kimi / GLM / Claude？
- **决定**：①客户端 provider 无关（全走 OpenAI 兼容协议，换模型=改配置）；②默认 deepseek-chat（便宜+中文强）；③选型结论用自建黄金集实测得出（Week 3 多模型对比实验），不靠猜；④LLM-as-Judge 裁判**故意用与主力不同家的模型**——避免 self-preference bias（模型评自己输出会系统性偏高）。

## D5：命名 AIRadar

- **过程**：TradeWinds（被主人否：名字必须含 AI、与 AI 资讯相关）→ AIRadar（主人拍板）。
- **为什么成立**：雷达意象三合一——每天定时扫描（cron pipeline）、过滤杂波（信源筛选）、航迹跟踪（话题时间线=记忆）。名字不塞属性，属性交给 slogan：「每天扫描 AI 前沿、沉淀为知识库的情报 Agent」。产品命名原则：名字管记住，slogan 管说清（参照 Cursor/Copilot 都不解释自己）。

## D6：HITL = 置信度路由 + GitHub Issue 审批卡片

- **背景**：全自动会放走坏内容，全人工回到技术周刊的人力瓶颈。
- **决定**：triage 综合分（tier 基础分 55% + LLM 价值分 45%）三分支：高分自动发布 / 中间区开 GitHub Issue 勾选审批 / 低分丢弃留日志。Tier D 信源强制送审（新信源无信誉记录，不给自动发布权）。审批决策写 feedback.jsonl，每周回流：信源近期通过率持续走低 → 自动产生降 tier 建议（数据飞轮）。
- **为什么用 GitHub Issue**：零基建的异步审批收件箱，天然有通知、有审计记录，Actions 有权限读写。对标的是企业级 Agent 平台里"高风险操作强制人工审批卡片"的同构简化版。

## D7：降级路径的设计原则——保守降级

- **决定**：LLM 不可用/超预算时：S/A 信源放行、B/C/D 全部送人工审；摘要环节降级为"仅标题+链接入库"并打标。
- **为什么**：降级的方向必须是"宁可多麻烦人，不可错发内容"——发布质量是产品信任的底线，降级时收紧而不是放宽自动化权限。所有降级留痕（item.notes + stats），可审计可复盘。预算硬上限（token/调用次数）保证跑不穿钱包。

## D8：Anthropic 信源接入（真实的信源工程案例）

- **背景**：Anthropic 官网无 RSS（2026-08 核实 anthropic.com/rss.xml 404）。
- **过程**：RSSHub 公共实例（rsshub.app）→ 实测 403（公共实例限流不可靠）→ 社区镜像 Olshansk/rss-feeds（GitHub Actions 自动生成的 RSS，raw.githubusercontent 直读）→ 实测 200 且当天内容在列 → 采用。
- **启示**：权威信源 ≠ 好抓的信源；信源工程需要"官方 → 社区镜像 → 兜底记录失败"的层级方案。单信源失败不阻塞全局（fetch 层 try/except per source）。

## D10：跨厂商降级链（primary → fallback → 优雅退场）

- **背景**：主人同时提供了 DeepSeek / Kimi / GLM 三家 key。三家都用，但角色必须分清，不能"随便挑一个"。
- **决定**：三家各司其职——
  - **主力（干活）**：DeepSeek `deepseek-v4-pro`——中文强、便宜，pipeline 的 triage/摘要/分类都用它
  - **备用（兜底）**：GLM `glm-5.3`——主力出现**永久性故障**时自动接管（跨厂商，避免单一供应商故障导致整条 pipeline 瘫痪）
  - **裁判（评测）**：Kimi `kimi-k3`——只在评测环节当 LLM-as-Judge，**故意与主力不同家**，避免模型给自己的输出打高分（self-preference bias）
- **实现要点**：供应商永久性故障后**标记作废，本次运行不再尝试**——不是每条内容都重试一遍。这是效率的关键：50 条内容 × 3 个 stage 的场景下，这个设计省掉约 25 分钟的无效等待。
- **模型清单来源**：直接查各家 `/models` 接口实测（2026-08-28），不靠记忆猜测——LLM 的训练知识对模型版本这类高频变动信息天然过期。实测发现 DeepSeek 已是 v4 代、Kimi 已到 k3、GLM 已到 5.3，全部新于我的知识截止。**教训：涉及模型/API 版本，先查再写。**

## D11：429 不等于限流——错误分类必须看语义，不能只看状态码

- **背景**：配好三家 key 后首次冒烟测试，三家全部调用失败。
- **发现**：同样是"账户没钱"，三家返回的状态码完全不同——DeepSeek 返回 **402**（标准的"需要付款"），而 **Kimi 和 GLM 都返回 429**（通常表示限流）。
- **问题**：我原来的重试逻辑把 429 一律当作"可重试的限流"，会对余额不足这种**永久性故障**做三次指数退避重试（1.5s+3s+6s）。50 条内容的日常运行会空转约 25 分钟才失败退出。
- **决定**：错误分类不看状态码，看**语义**——429 的响应体里若命中余额/配额特征词（insufficient balance / suspended / 余额不足 / 无可用资源包 / quota），判定为永久性故障，立即换供应商，绝不重试。
- **验证**：写了 12 个回归测试锁住这套逻辑（`evals/test_llm_guards.py`），并在真实的三家零余额环境下做了端到端降级演练——主力 402 → 备用 429（语义识别为永久）→ 全挂 → 三个 stage 各自降级 → pipeline 照常跑完并发布了 3 条 S 级内容。
- **面试价值**：这是"兜底逻辑"从口号变成真东西的分水岭。绝大多数人写重试只按状态码，而真实世界的 API 语义是混乱的——**只有真跑过、真失败过，才会知道这件事**。

## D12：模型适配层——"OpenAI 兼容"并不真的兼容

- **背景**：三家都号称 OpenAI 兼容协议，但首次真实调用时两家直接报错或返回空。
- **实测差异**（2026-08-28）：
  - `kimi-k3` 只接受 `temperature=1`，传 0.2 直接 HTTP 400。
  - **三家的旗舰模型全都是推理模型**（deepseek-v4-pro / kimi-k3 / glm-5.x 都返回 `reasoning_content`），而**内部思考的 token 也计入 `max_tokens`**。实测 glm-5.3 在 `max_tokens=300` 时，思考就用掉 299 个 token，`content` 返回空字符串、`finish_reason=length`。deepseek-v4-pro 连"输出 {"a":1}"这种琐碎请求都要花 108 个思考 token——这正是首次运行时摘要环节 JSON 解析失败的真正原因。
- **决定**：加一层**模型适配层**（`llm.py` 的 `MODEL_QUIRKS`），按模型名前缀声明每家的怪癖（温度约束、token 倍率），调用逻辑不变。另加**自愈机制**：检测到"空 content + finish_reason=length"就自动加倍预算重试一次。
- **为什么这样分层**：新增模型只改一张表，不动调用代码；怪癖是**数据**不是**逻辑**。这对应 Agent 平台里"Tool 协议适配层"的思路——上层要一个统一契约，下层的脏活集中在适配层消化。
- **面试价值**：这是"模型能力边界"的具体体感。推理模型的 `max_tokens` 语义变了（要覆盖思考+输出），不知道这件事的人会在生产环境遇到"模型莫名返回空"，且极难排查。

## D13：内容获取降级链（直接抓取 → Jina Reader → RSS 简介）

- **背景**：首次真实运行发现 **OpenAI 的全部条目**都抓不到正文（`fulltext_failed`），RSS 里只有 150 字的一句话简介。
- **排查**：openai.com 由 Cloudflare 防护，实测直接抓取 403，**换成完整浏览器 UA 依然 403**——它拦的是非浏览器客户端本身。
- **决定**：内容获取也做降级链（与 LLM 降级链同构）：直接抓取 → Jina Reader（`r.jina.ai`，第三方正文提取服务，实测能拿到 53,975 字）→ 失败则保留 RSS 简介。每层结果记入 `item.extra.content_source`，前端可展示"内容完整度"。
- **取舍**：引入了一个外部依赖（Jina），但它只是兜底层、失败不阻塞，且换来了权威信源的完整正文——这是值得的交换。

## D14：信息不足时不许模型硬编（真实幻觉的根因修复）

- **背景**：首次真实运行的幻觉自检**抓到了一条真幻觉**——摘要写"loveholidays 用 Codex 让**全公司员工都能构建软件**"，而原文只说"让软件开发在整个企业内变得**可及**"。
- **归因**：这不是模型不老实，是**我们的 prompt 逼它编**——只给它 150 字的简介，却要求写 250-350 字的摘要，缺的信息只能靠猜补足。
- **决定**：`summarize` 按原文长度分两种模式。原文 < 400 字进入**简介模式**：只写一句话概括、`summary_long` 故意留空，prompt 明确告知"你拿到的只是简介，绝对不许推测或扩写"。前端据此展示"内容完整度"标记。
- **面试价值**：这是幻觉治理的正确姿势——**先归因再修**。归因结论是"评测问题/数据问题/prompt 问题/模型问题"中的**prompt 与数据问题**，而不是换个更强的模型。同一逻辑还有旁证：Kimi k3 只看标题时曾编造"这是 Anthropic 的愚人节玩笑"（重跑一次又变正常，说明是随机幻觉），喂上原文后判断完全准确——**信息不足是幻觉的第一诱因**，这反过来验证了 D2（自己抓原文再喂给模型）。

## D15：并发化——从 8 分钟 6 条到全量可用

- **背景**：首次真实运行 6 条内容耗时 **8 分 05 秒**（每条 80 秒）。推理模型单次调用要 5-30 秒，而每条内容要经过 triage/summarize/幻觉自检/classify 共 3-4 次调用。按此速度，40 条内容的日常运行要接近 1 小时。
- **决定**：抓取与三个 LLM stage 全部改为线程池并发（`guards.parallel_map`，标准库 `ThreadPoolExecutor`，不加新依赖）。并发度默认 6。
- **必须配套的正确性处理**：共享状态加锁——`Budget`（`+=` 在多线程下不是原子操作，会漏记 token 导致预算失控）、`LLMClient.stats`、供应商作废标记（避免重复打印降级日志）。单条失败仍被隔离，不影响同批其他条目（舱壁原则的并发版）。
- **为什么用线程而不是 async**：LLM 调用是纯 I/O 等待，线程池足够；改 async 要把 requests 换成 httpx 并重写整条链路，收益不抵成本。

## D16：并发度是被限流打出来的，不是拍脑袋定的

- **背景**：并发度设 6 跑全量后，日志里出现 GLM 的 `429 code 1302 您的账户已达到速率限制`，导致部分条目"所有供应商均不可用"而降级。
- **决定**：并发度降到 4；同时把临时性故障的退避从"3 次 / 基数 1.5 秒"改成"4 次 / 基数 4 秒"——真限流需要几十秒才恢复，退避太快只会继续把配额打满，形成自我强化的失败。
- **配套**：真限流（TransientError）与余额不足（permanent）走完全不同的路径，这正是 D11 那次错误分类修复的价值兑现——如果两者混在一起，这里要么该退不退，要么不该退瞎退。
- **面试价值**："并发度设多少"没有理论最优解，只能压出来。有意义的是**有没有观测手段发现它、有没有机制在它发生时不崩**。

## D17：让系统自愈，而不是手工调参

- **背景**：全量运行后发现 triage 有 2 条 `llm_json_invalid`、classify 有 9 条降级到启发式规则。根因还是 D12 那个推理模型问题——triage 给了 200 token、classify 给了 150 token，思考一花完就没预算写 JSON 了。
- **两种修法**：(a) 手工把每个 stage 的 max_tokens 调大；(b) 让客户端检测到截断（`finish_reason=length`）就自动加倍预算重试。
- **决定**：**两个都做，但以 (b) 为主**。原先的自愈只处理"content 完全为空"，现在扩展为"只要被截断就自愈"——因为截断的另一种形态是"半截 JSON"，解析失败但 content 非空，原逻辑漏掉了它。
- **为什么**：手工调参是一次性的，换个模型、改个 prompt 长度就又失配；自愈是结构性的。**能让系统自己恢复的，就不要靠人记得调参数。**

## D18：幻觉的第二个根因——元数据被当成了正文

- **背景**：修复 D14 后跑全量，幻觉检测抓到 4 条。逐条归因发现其中 3 条同源。
- **真实案例**：
  - 摘要写"**谷歌 DeepMind** 宣布…"，但原文通篇只说 Google——模型把**信源名**（Google DeepMind Blog）当成了文章内容。
  - 摘要写"**Simon Willison** 引用了 Paul Dix 的观点"，原文根本没提 Simon——博客主的名字被写成了文章作者。
  - 一条 HN 条目，模型从标题"CEO fired developers to make room for AI"编出整段背景故事，而该链接的实际内容是一个开源项目介绍（**HN 的标题是网友写的，与链接文章不是一回事**）。
- **归因**：不是模型能力问题，是 **prompt 设计问题**——我们把标题、来源名和正文平铺在一个 prompt 里，模型无从区分哪些是"关于这篇文章的元数据"、哪些是"这篇文章说了什么"。
- **决定**：① prompt 里用分隔线把【元数据（仅供参考，不是文章内容）】和【原文】明确切开；② 加三条铁律：元数据不是内容、不许补背景、不许外推结论。
- **验证（受控实验）**：拿被标记的原条目用新旧 prompt 各跑一遍——"谷歌 DeepMind"→"Google"修复；HN 那条改为正确摘要真实文章内容；"Simon Willison"张冠李戴消失。
- **意外收获**：修复后裁判在同一条上抓到了**更隐蔽的一类幻觉**——摘要漏掉原文的前提条件（"在构建验证系统并给予适当方向的前提下"），把有条件的结论表述成了无条件。这类"因省略而失真"比"无中生有"难发现得多，说明 LLM-as-Judge 确实在产生规则校验给不了的信号。
- **面试价值**：完整演示了 JD 里点名的归因能力——**从失败轨迹抽象假设 → 设计受控实验 → 验证 → 判断是模型问题还是 Harness 设计问题**。这里两次归因结论都是 Harness/prompt 问题，而不是"换个更强的模型"。

## D19：已知运行约束——个人账户的速率限制

- **现象**：36 条内容的一次运行要打 ~122 次 LLM 调用（每条约 3.4 次：评分/摘要/幻觉自检/分类），期间数次撞到 GLM 的 `429 code 1302 速率限制`，个别条目最终降级。
- **现状**：并发度 4 + 4 次退避（基数 4 秒）下，降级率已从 17% 降到 3%（36 条里 1 条）。
- **尚未做但已知的优化方向**（Week 3 视情况）：按供应商维度做令牌桶限速、把幻觉自检改为抽样而非全量、给 triage 用更便宜的 flash 模型（`deepseek-v4-flash` 实测 2.4 秒 vs pro 的 5.6 秒且评分质量相当）。
- **诚实记录**：这是个人账户的额度限制，不是架构缺陷；但**知道自己的瓶颈在哪、有没有可选的降本方案**，本身就是 Token 治理能力的一部分。

## D20：前端设计——雷达不是装饰，是数据可视化

- **背景**：前端要在 3 秒内让人（尤其是面试官）看懂这个产品在干什么。
- **决定**：整体走「仪表盘 / 信号情报终端」——深色仪器底、琥珀色代表有效信号、青色代表结构与扫描。字体用 Instrument Serif 做刊头 + IBM Plex Mono 做数据读数 + IBM Plex Sans SC 做中文正文，制造「编辑部 × 仪器」的张力（这正是产品定位：干的是资深编辑的活，用的是机器的方式）。
- **签名元素**：右栏的雷达示波器**绑定真实数据**——半径 = 综合分（越靠中心越可信）、角度 = 内容分类扇区、颜色 = 时间维度（琥珀=时效 / 青绿=长期价值）、大小 = 分数。筛选时雷达同步更新：点「论文」，5 个绿点；切到「待审队列」，光点全部落在外圈。**隐喻和数据是一致的，不是套壳。**
- **「机制」页**：产品的自我说明书——pipeline 六环节、信源分层准入逻辑、置信度路由阈值、三条降级链（附真实故障案例）、评测方法、最近一次运行的真实读数。面试官打开这一页就能看懂整个系统。
- **诚实标注**：抓不到原文的条目在卡片上标「简介级」并说明原因。**承认信息不完整，比假装完整更可信**——这与 D14 的反幻觉原则一脉相承。
- **可读性实测**：深色底上 300 字重的中文过细，实测调到 400 才清晰；正文对比度也相应上调。

## D21：六级信源体系一度只跑了三级——文档与实现的偏差

- **怎么发现的**：主人读 `docs/mechanisms.md` 时问"B 是垂直媒体和社区信号具体有什么？是不是漏了对 C 的介绍？D 一般是什么样子？"——一查，文档确实漏写了 C 级；**再一查 `sources.yaml`，发现 C/D/X 三级根本是空的**（S 7 个、A 4 个、B 2 个，其余为零）。
- **问题的严重性**：文档和前端「机制」页都在描述一套六级体系，实际只跑了三级。面试官问"你的 C 级信源有哪些""D 级强制送审这条路径真跑过吗"，就会当场露馅。**这不是文档笔误，是设计写了但没落地。**
- **两种修法**：(a) 把文档改成只讲三级，承认其余是规划；(b) 把信源补齐，让六级真的跑起来。
- **决定：选 (b)**，因为 D 级那条路径是整个信誉体系的活性证明。补了：
  - **C 级（投资/研究/跨界）**：SemiAnalysis（算力与供应链约束）、AI Snake Oil（Princeton 研究者的批判视角）、Import AI。**刻意引入批判性声音**——只收官方发布和乐观派分析，知识库会变成信息茧房。
  - **D 级（待观察）**：Latent Space、Interconnects、Eugene Yan。
  - **X 级保持空**：还没遇到需要屏蔽的源，机制已就位。不为了凑满六级去编造。
- **D 级选源的关键理由（这是最好的那句话）**：这三个信源**质量其实很高**，放最低级不是因为它们差，而是因为**它们在本系统里还没有信誉记录**。所有新信源一律从 D 级进入、强制人工过审；人工连续通过率高了，`hitl._source_hint` 才给出升级建议。**信誉是挣来的，不是我赐的**——tier 由此从"我手工贴的静态标签"变成"有升降通道的信誉记录"。
- **面试价值**：这条决策的价值不在于补了几个信源，而在于**承认并修复了"设计文档跑在实现前面"这类偏差**。产品经理最容易犯的错就是 PRD 里写得很完整，上线的东西只实现了一半——而且自己不知道。这里的教训是：**文档里每一个具体断言，都应该能在代码或数据里指到对应的东西。**

## D22：信源会"沉默地死掉"——所以要有体检机制

- **怎么发现的**：补完 C/D 级信源后逐个实测，发现两个信源其实已经死了，但**系统完全不知道**：
  - **SemiAnalysis**：公开 RSS 停更在 2025-09（内容转付费），但 feed 本身能正常解析，每天照常被抓取、照常返回 0 条。
  - **机器之心**：`/rss` 路径返回 **HTTP 200，但内容是 HTML 网页而不是 feed**。不报错、不告警，只是永远抓 0 条。
- **问题的本质**：这是**沉默的失败**（silent failure）——不抛异常、不触发任何降级路径，因此所有兜底机制都失效。信源池就这样慢慢腐烂，而运行日志一片绿色。
- **决定**：加 `pipeline/sources_health.py` 体检命令，报告每个信源的最新内容日期与存活状态。
  - 替换两个死信源：SemiAnalysis → Dwarkesh Podcast（巧的是它最新一期的嘉宾正是 SemiAnalysis 创始人 Dylan Patel）；机器之心 → 量子位（实测每天更新）。
- **两个误报也修了，比修死信源更能体现设计能力**：
  - **阈值不能一刀切**：Karpathy 119 天没发文，但他本来就发得少——用统一的 90 天阈值会把"低频但活着"误判成"死了"。改成按 tier 分档（S 级 30 天，A 级 180 天）。
  - **查询型信源不适用"最新一篇"这个指标**：HN 搜索和 GitHub 搜索是按条件查，不是按时间流，对它们只报"当前窗口能否查到内容"。**指标要匹配对象的性质，套错了指标只会产生噪声告警——而噪声告警最终会让人忽略所有告警。**
- **顺带修了一个真 bug**：体检时崩在 `datetime.fromisoformat('2026-08-18T04:08:11Z')`——Python 3.10 不认 `Z` 后缀（3.11 才支持），而 GitHub API 返回的正是这种格式。说明**库里的时间格式不统一**，违反了项目自己定的"所有时间存 UTC ISO"约定。已加 `parse_iso` / `norm_iso` 从源头统一。
- **面试价值**：可观测性的真正难点不是"挂了要报警"，而是**"没挂但也没在工作"这种状态怎么发现**。前者任何异常捕获都能做到，后者必须主动去量。

## D23："保护"和"碰巧没出事"是两回事

- **怎么发现的**：给置信度路由补回归测试时，"D 级信源即使满分也不能自动发布"这条断言**失败了**——状态确实是 review（对的），但预期的 `tier_D_forced_review` 标记没出现。
- **追查**：算了一下 D 级的分数上限——`0.55 × 30（D 的基础分） + 0.45 × 100（内容满分） = 61.5`，够不到 75 的发布线。**所以 triage 里那条显式的"D 级强制送审"规则从来没有执行过，是死代码。**
- **这为什么是个问题**：保护确实生效了，但它是**靠算术碰巧成立的**，不是靠那条规则。只要有人把 D 的基础分从 30 调到 60，或者把发布线从 75 降到 65，保护就**静默失效**——没有报错、没有测试变红、没人会发现。
- **决定**：保留显式规则（它是真正的安全网），但把测试改成**验证安全网本身**而不是验证当前配置下的结果：测试里临时把发布线调低到 50，模拟一次未来的配置变更，确认那条规则真的会兜住并留痕。同时加一条不变量测试：D 级在 20/50/75/90/100 各档分数下都不得被自动发布。
- **面试价值**：这是**测试该测什么**的一个具体例子。测"当前跑出来的结果对不对"只能防止今天的错误；测"不变量在参数变化下是否仍然成立"才能防止明天的错误。很多安全机制在生产环境里是死的——不是因为写错了，而是因为**它依赖的前提条件悄悄变了，而没有任何东西在守护那个前提**。

## D24：黄金集测出"高召回低精度"——于是产品分两层，而不是调阈值

- **数据**（主人标注 26 条后首次评测）：**召回 100%，精确率 52%**。混淆矩阵 tp=13 / fp=12 / fn=0 / tn=1——系统只丢弃了 1 条，而主人想丢 13 条。
- **两种解读**：
  - 悲观："筛选器不准，一半是噪声。"
  - 准确：**"筛选器是高召回型的。"** 它没漏掉任何一条主人真正想要的内容，代价是放进来一批可有可无的。
- **决定：不调阈值，改产品形态**（主人拍板方案 B）。调高阈值能提精度，但会牺牲召回——而对情报系统来说**漏报比误报代价高得多**。所以分两层：
  - **每日 feed**：保持宽松（recall 优先）。目标是"3 分钟扫完今天发生了什么"，看完就过。
  - **知识库精华**：严格（precision 优先）。只有经过人工审批认可的才长期留存、可检索。
- **这不是妥协，是把一个指标冲突拆成两个产品面**：同一套数据、两种消费方式，各自优化各自的指标。
- **面试价值**：这是"评测驱动产品决策"的完整链路——自建黄金集 → 测出指标画像 → **从指标画像推导产品形态**，而不是从指标画像推导参数调整。很多人做评测停在"分数变高了"，而评测真正的用处是**告诉你系统是什么性格，然后为这个性格设计产品**。

## D25：分类改为多标签 + 拆出「模型训练」

- **来源**：主人复核黄金集时的真实反馈——"我对于每条的分类有的时候不只是只分类在一个类别中"，并具体指出一篇讲量化训练的 arXiv 论文既是「论文」又该是「模型训练」，而「模型训练」当时不存在。
- **两处改动**：
  1. `category`（单值）→ `categories`（多值，1-3 个）。保留 `category` 作为主分类（=categories[0]），老数据自动迁移，前端筛选改为"包含即匹配"。
  2. 新增「**模型训练**」类别，与「模型发布」分开——前者讲**怎么练出来的**（预训练/微调/蒸馏/量化/后训练），后者讲**发布了什么**。同时把「工程实践」收窄为系统层内容（生产部署、架构运维、可观测性），不再兜底一切工程话题。
- **为什么多标签是必需的而不是锦上添花**：「论文」其实是**体裁**标签，而「模型训练」「Agent 工程」是**主题**标签，两者正交。单选会强迫在体裁和主题之间二选一，信息必然丢失。（技术周刊的"双轴分类"是同一个洞察：来源/体裁 × 技术方向。）
- **数据库迁移的原则**：加字段不能靠重跑 pipeline 补数据——已有的运行记录是项目资产。所以 `db.py` 加了轻量迁移：检测缺列就 ALTER TABLE 并用旧字段回填。

## D26：同一类错误犯了两次——凡是版本号，先查再写

- **第一次（D10）**：写模型名时差点凭记忆写 `deepseek-chat`，实测查 `/models` 接口才发现已经是 `deepseek-v4-pro`，Kimi 到 k3、GLM 到 5.3，全部新于我的知识。
- **第二次（本次）**：重写 `web/package.json` 时凭记忆写了 `typescript@~5.9.4`、`vite@^7.2.7`、`@vitejs/plugin-react@^5.1.1`——**三个版本号全是错的**（实际是 6.0.3 / 8.2.2 / 6.1.0，其中 typescript 5.9.4 这个版本压根不存在）。GitHub Pages 首次部署因此挂掉。
- **为什么本地没暴露**：本地跑的是脚手架装好的包，`npm install` 对不上的版本会宽容处理；而 CI 用 `npm ci`，它严格按 lockfile 装、对不上直接失败。**"本地能跑"和"干净环境能装"是两件事。**
- **修法**：从 `node_modules` 读实际安装版本回写 `package.json`，重新生成 lockfile，并**在一个干净目录里跑一遍 `npm ci` 验证**——复现 CI 的环境，而不是相信本地。
- **顺带暴露的第二个问题**：重新生成 lockfile 后构建报 `Cannot find type definition file for 'node'`——`vite.config.ts` 用了 `process.env`，需要 `@types/node`，之前是靠传递依赖侥幸拿到的。**依赖收紧后，隐式依赖会现形。**
- **沉淀成规矩**（已写进 CLAUDE.md）：**任何版本号——模型 ID、包版本、API 版本——都必须先查实际值再写。** 训练知识对这类高频变动信息天然过期，而它们的失败方式往往是"本地好好的，一上线就挂"。

## D27：数据飞轮的统计陷阱——反馈只来自中间区，是有偏样本

- **触发**：主人首次完成 18 条人工审批后，回收数据显示：
  | 信源 | 边缘区通过率 |
  |---|---|
  | GitHub Trending（**B 级**） | 3/9 = 33% |
  | OpenAI News（**S 级**） | 0/4 = **0%** |
  | Hacker News（**A 级**） | 0/4 = **0%** |

  主人放行的 3 条**全部来自 B 级信源**，S/A 级的边缘内容一条没要。
- **错误的结论**："信源分层失效了，S 级还不如 B 级，应该降 OpenAI News 的 tier。"
- **正确的归因**：**人工反馈只存在于中间区（50–75 分）**——高分内容自动发布了、低分内容直接丢了，两头都没人打过分。所以这个通过率是**条件概率** P(人工认可 | 落在边缘区)，不是信源的整体质量。
  - OpenAI News 的**好东西全在高分区**（黄金集里主人认可了它多条高分内容），落到边缘区的恰恰是"巴西市场扩张""学生使用调研"这类营销软文。
  - GitHub Trending 相反：它没有营销稿，边缘区的内容依然是具体的技术产出（unlazy skill、pi-from-scratch、deepseek-harness），所以边缘区通过率反而高。
- **决定**：`_source_hint` 只给**边缘区处理策略**建议（"该信源的边缘内容多半没价值，可提高其送审门槛，少占人工注意力"），**绝不建议调整 tier**——用有偏样本去推翻无偏结论是统计上的硬错误。同时把样本门槛从 5 提到 8（边缘区数据本就稀疏）。
- **面试价值**：这是数据飞轮最容易翻车的地方，而且翻了车很难发现——因为数字看起来完全合理（"S 级通过率 0%，那肯定要降级啊"）。**任何"用线上行为数据反馈优化"的系统都要先问一句：这批数据是怎么被采样出来的？** 我们的采样规则恰好是"系统不确定的才给人看"，所以人看到的永远是最难判断的那一批，用它评价信源整体必然失真。（同类问题在推荐系统里叫 selection bias / 幸存者偏差。）

## D28：评测污染——人工审批覆盖了系统的判断，评测变成"人评人自己"

- **怎么发现的**：主人问"黄金集只有 26 条够 Week 3 用吗"。查证时发现，26 条里有 **10 条的 `status` 已被主人自己的 HITL 审批改写**。而评测用 `status != 'discarded'` 代表"系统的判断"——对这 10 条来说，"系统判断"就是"主人的判断"，评测在比较**主人 vs 主人自己**，必然一致。
- **后果**：精确率虚高（含污染 71% vs 真实 48%），且**越用越糟**——每天审批越多，被覆盖的条目越多，有效样本越少。当时有效样本已从 26 掉到 16。
- **这个 bug 的诞生方式值得单独记**：它不是一直存在没被发现，而是**随 HITL 上线才产生的**。HITL 之前，没有任何条目被人改写过，`status` 就等于系统判断，评测是准的。**新机制破坏了旧机制赖以成立的前提。**
- **修复**：加 `auto_status` 字段冻结 triage 的原始路由结论，HITL 只改 `status`、永不碰 `auto_status`，评测只看 `auto_status`。
  - **历史数据 100% 可恢复**：只有 `review` 状态的条目才会进审批 issue，所以凡在 `feedback.jsonl` 里出现过的 id，其 `auto_status` 必然是 `review`。迁移时据此反推，18 条全部还原，**主人已标的 26 条一条不用重标**。
  - 评测报告新增 `usable` / `no_auto_status` 字段——污染若再发生，一眼可见。
- **原则**：**系统的判断和人的判断，必须是两条独立记录、永不互相覆盖的轨迹。** 只有这样才能永远回答"系统当初自己判，判对了吗"。
- **面试价值**：任何带人工反馈的 AI 系统都会遇到这个坑——人的修正会污染掉"模型原本表现"的记录。而且它极其隐蔽：指标不会报错，只会悄悄变好看。**上线人工反馈机制时，第一件事是确认它不会覆盖任何用于评估的字段。**

## D29：三分类路由不能用二分类指标评价

- **背景**：修完 D28 后重跑评测，精确率显示 48%，看着很差。但细看发现算法把"送人工审"的条目算成了"系统认为该收"。
- **问题**：我们的 triage 有**三种输出**——`published`（我认为该收）、`discarded`（我认为该丢）、`review`（**我不确定，你来定**）。用二分类的 precision/recall 评价它必然失真：
  - 把 review 算成"该收" → 把**谨慎**当成了**错误**
  - 把 review 算成"该丢" → 把**求助**当成了**拒绝**
- **决定**：三条路径分开评，各自有各自该优化的指标：
  | 指标 | 含义 | 实测（n=26） |
  |---|---|---|
  | 自动发布准确率 | 自动发布的里面人认可的比例（**错发代价最高**） | 15 条 → 67% |
  | 自动丢弃准确率 | 自动丢弃的里面人也认为该丢的比例 | 1 条 → 100%（**样本仅 1 条，等于没测**） |
  | 送审命中率 | 送人工审的里面人最终认可的比例（**太低=浪费人的注意力**） | 10 条 → **20%** |
  | 漏网之鱼 | 人想要但被系统自动丢弃的条目，逐条列出 | **0 条** |
- **这个评法立刻暴露了二分类指标看不见的问题**：**送审命中率只有 20%**——主人花时间审的 10 条里只有 2 条值得收，80% 的审批注意力被浪费。这是明确的产品缺陷，而在旧的"精确率 48%"里完全看不出来。
- **由此得到的可行动结论**（样本量够了再执行）：送审区间的下界（50 分）应该提高，让明显没价值的直接丢弃而不是占用人工；自动发布阈值（75 分）可能偏低。
- **面试价值**：**指标必须匹配系统的输出结构**。这跟 D22 里"查询型信源不适用'最新一篇'指标"是同一个道理——套错指标不会报错，只会给出看似合理实则误导的数字。另外注意：这里"自动丢弃只有 1 条样本"直接印证了黄金集低分段欠采样的问题，两个发现互相印证。

## D30：内容过期——时效的会退场，长期的和人认可的永不遗忘

- **来源**：主人的原话——"对于营销宣传类的消息我都没纳入……不是说在平台上完全不显示，只是时间一长会被自动删掉，你觉得呢？"
- **决定**：知识库（`db.archive_items()`）按三条规则筛：
  1. `horizon == 'short'`（时效类）且**未经人工审批认可**的条目，发布超过 14 天后退出知识库
  2. **人工审批认可过的永不过期**——那是主人明确说"这个我要留着"的东西，机器无权代为遗忘
  3. `horizon == 'long'`（方法论/原理）永不过期
- **为什么是"过期"不是"删除"**：数据仍留在库里，只是不进知识库视图。理由与 D9 一致——"三个月前判死了哪些、判对了吗"必须能复盘。**能被遗忘的产品可以，不能被审计的产品不行。**
- **产品形态由此定型**（D24 的方案 B 落地）：**feed 是流水，知识库是沉淀**。流水冲走杂质（时效内容自然退场），沉淀留下金子（长期价值 + 人工认可）。

## D31：数据跨度不够时，不许给趋势结论

- **背景**：话题趋势模块（`pipeline/memory.py`）跑出来后，25 个话题**全部显示"萌芽"或"升温"**。看起来像个大发现——AI 领域到处都是新话题在爆发。
- **但这是错觉**：判断"萌芽"的规则是 `90 天窗口计数 == 7 天窗口计数`，而知识库当时只有 18 天数据，**任何话题都必然满足这个条件**。不是话题新，是**我们的记忆太短**。
- **决定**：加 `MIN_SPAN_DAYS = 21` 守卫。知识库覆盖跨度不足时，生命周期一律标"观察中"，并在前端明确写出"知识库目前只覆盖 N 天，还不足以判断趋势"。**热度数字照常显示（那是真实的），但不给趋势结论。**
- **面试价值**：这是同一类错误的第三次出现，也是最隐蔽的一次——
  - D22：指标要匹配**对象的性质**（查询型信源没有"最新一篇"）
  - D29：指标要匹配**输出的结构**（三分类路由不能用二分类指标）
  - D31：指标要匹配**数据的跨度**（18 天数据算不出 90 天趋势）

  三次的共同点是：**套错了的指标不会报错，只会给出看起来很合理、实则误导的数字**。而"看起来很合理"正是它危险的地方——如果我不较真，这个趋势页会带着 25 个假的"萌芽话题"上线，而且看着还挺唬人。

## D32：基础设施故障不能被统计成模型质量问题

- **怎么发现的**：LLM-as-Judge 幻觉评测首次跑，报告"幻觉率 20%"。但逐条看时发现，那条被判"不忠实"的条目，问题描述写的是 `judge_error: 限流 http 429`——**它根本不是幻觉，是裁判模型被限流了**。
- **根因**：我把"裁判调用失败"和"裁判判定不忠实"塞进了同一个 `problems` 列表。于是一次限流就变成了一条幻觉记录，**幻觉率被基础设施故障污染**。
- **更糟的是数字本身**：抽样 10 条，只有 5 条成功判定，"20%"实际是 1/5 —— 这个样本量下的幻觉率没有任何意义，但报告里它看起来和别的指标一样正经。
- **修复**：
  1. **错误与判断严格分离**：调用失败进 `errors`，模型判断进 `votes`，两者永不混合。
  2. **最少票数门槛**：k 次判断中至少要有 2 次成功才下结论，否则这条**跳过**并明确记录原因——**绝不默认判它有问题**。
  3. 报告里分开显示"判定 N 条 / 跳过 M 条"，跳过的不计入分母。
  4. 裁判改串行 + 每次调用间隔 2 秒——kimi-k3 限流严格，慢一点无所谓，评测不是每天跑。
- **这是"指标要匹配数据"的第四次出现**（D22 对象性质 / D29 输出结构 / D31 数据跨度 / D32 **数据来源的可靠性**）。这次的形态最阴险：**指标被自己的测量工具的故障污染了**。
- **一条通用的原则**：**任何自动评测都必须能区分"被测对象不合格"和"测量过程失败"。** 分不清的话，你的系统越不稳定，指标看起来就越差——而你会以为是模型变差了，跑去调 prompt，实际上该修的是限流。

## D33：LLM-as-Judge 的随机性要靠投票，不是靠假装它稳定

- **背景**：裁判用 kimi-k3，而它**强制 temperature=1**（D12），同一条内容重复问会给出不同答案。单次采样得到的"幻觉率"是个随机数，不是指标。
- **决定**：每条判 **k=3 次取多数票**，同时记录**裁判自己的分歧率**（k 次判断不一致的条目占比）。
- **为什么要单独报分歧率**：它区分了两种完全不同的情况——
  - 分歧率低 → 裁判判断稳定，幻觉率可信
  - 分歧率高 → **那些条目本身处于灰色地带**（摘要是否忠实见仁见智），而不是"裁判不靠谱"
  把这两种情况混为一谈，会让人误以为该换个"更稳定的裁判模型"，而真实情况可能是任务本身就没有唯一答案。
- **这是 pass@k 稳定性评估思路的简化应用**：不追求单次结果，而是测量结果的分布。

## D9：discarded 条目也入库

- **决定**：被筛掉的内容不是删掉，而是以 discarded 状态入库。
- **为什么**：①审计——"筛掉了什么"和"收了什么"同样是筛选器质量的证据；②评测——黄金集里 include=false 的样本需要 pipeline 决策记录才能算 precision/recall；③回溯——阈值调整后可以复盘历史误杀。
